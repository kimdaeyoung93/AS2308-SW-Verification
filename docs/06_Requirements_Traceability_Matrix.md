## Interpretation rules

- Requirement compliance evidence is the healthy MIL result produced by the applicable deterministic Oracle or the explicitly identified static/configuration method.
- `PASS`, `APPLICABLE`, `ESTABLISHED`, `INCONCLUSIVE_PRECONDITION`, `EXECUTION_ERROR` and `N/A` retain the meanings defined by the frozen artifacts. This matrix does not create new statuses.
- Mutation linkage distinguishes a semantically related fault from an execution that actually killed the mutant. Only corrected v1 results are authoritative; initial mutation results are not used.
- Coverage is suite-level structural evidence, not requirement PASS evidence. Requirement-level coverage percentages were not measured.
- SIL did not re-verify product requirements. A SIL entry only states whether a related frozen scenario was included in the Source-to-Derived gate, Phase A characterization or independent Phase B Model-Code comparison.
- A Phase B B2B `PASS` is generated-code numerical-equivalence evidence in the frozen host environment, not `REQ-XXX SIL PASS`, HIL, MCU or real-time evidence.

## Summary

- Requirement/environment ID count: **11** — 7 `REQ-*` requirements and 4 `ENV-*` constraints from Requirements v1.1.
- Manual Dynamic Compliance Suite: **5 logical Test Cases / 9 top-level executions**, all healthy `PASS`. A supplemental `MTC-006` specification exists only in the untracked working tree; it is not part of the committed authoritative baseline or this count.
- Official AI Suite: **9 top-level executions**, all healthy `PASS`; four requirement IDs are directly targeted (`REQ-VOLT-001`, `REQ-TRK-001`, `REQ-DIR-001`, `REQ-REV-001`).
- Mutation linkage: the corrected Primary Mutation Set contains **6 valid mutants**; Manual and AI each killed 6/6. Actual kill cells are recorded separately from semantic fault relevance.
- Coverage scope: Manual Suite DUT-level Execution **10/10** and Decision **4/4**; Condition and MC/DC are `N/A`. No requirement-level coverage percentage was produced.
- SIL B2B scope: **18** frozen Manual/AI candidate scenarios have SIL traceability. Three were used for Source-to-Derived/Phase A characterization and marked supplemental/non-independent for Phase B; the remaining **15** independent Phase B executions passed the frozen Model-Code numerical criterion.

> Requirement compliance evidence는 MIL Oracle 결과를 기반으로 하며, SIL evidence는 generated-code Model-Code equivalence를 나타낸다.

## Evidence gaps and traceability notes

1. `REQ-BW-001`, `REQ-PI-001` and the static structure/gain portion of `REQ-AW-001` are verified by `results/static_requirement_verification_v1/static_verification_summary.csv`. These static results do not create dynamic performance claims.
2. `REQ-AW-001` has static `PASS`, but no official dynamic recovery-compliance result CSV, AW-specific deterministic dynamic Oracle or selected AI Test Case. Dynamic effectiveness remains supplemental and `N/A` for compliance.
3. Coverage was aggregated for the Manual Suite/DUT. Requirement-level coverage was not measured.
4. SIL evidence is scenario-level Model-Code equivalence only. It is not requirement re-verification and provides no HIL, MCU, WCET or real-time timing evidence.
5. Existing working-tree provenance issue: untracked `tests/03_Manual_Test_Cases.csv` still names `MIL Baseline v2` in several Manual preconditions, while the authoritative execution/model is `AS2308_MIL_Baseline_v3`. TC IDs, inputs and Oracle mappings match the authoritative execution evidence, but the stale v2 text remains in the working specification and was not modified here. The untracked file is not used as primary evidence in this matrix.
